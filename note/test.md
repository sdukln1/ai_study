一、大模型与Agent开发
1. 熟悉RAG全链路（文档解析→文本切分（Chunking）→Embedding选型→向量检索→重排序（Rerank）→增强生成）
   1) 简要解释RAG   
      RAG（检索增强生成）的核心思想是“先查资料，再回答问题”，目的是解决大模型的幻觉问题合入知识时效性不足的问题。
   2) 文档解析（Document Parsing）  
      这是整个RAG系统的数据入口。原始数据格式多样（PDF、Word、Markdown、HTML、数据库等），文档解析层负责将这些非结构化或半结构化数据  
      提取为纯文本内容，同时尽可能保留文档的层级结构（如标题、段落、表格）。难点在于PDF中的表格解析和图文混排处理。
   3) 文本切分（Chunking）  
      解析后的文本通常很长（一本书可能有几十万字），而LLM的上下文窗口有限（即使有1M窗口，塞入大量无关信息也会影响召回精度）。Chunking的  
      核心任务是把长文本切分成语义完整的小块（Chunk）。切分策略很关键：切得太短会丢失上下文，切得太长则检索颗粒度太粗。常用的策略包括固定  
      长度切分（带重叠窗口）、基于语义的递归切分（按段落/句子边界切分），以及针对特定格式的切分（如Markdown按标题层级切分）
   4) Embedding选型（Embedding Model Selection）  
      切分好的文本块是“人类语言”，计算机无法直接理解，Embedding模型的作用是将文本转换成稠密的向量（一串浮点数数组），让语义相似的文本在  
      向量空间中距离更近。选型时需要在通用性（如openai的text-embedding-3系列）和垂直领域专业性（如BGE，GTE等中文优化模型）之间权衡。
   5) 向量检索（Vector Search）  
      当用户提出一个问题时，系统先将问题通过同样的Embedding模型转换成向量，然后在向量数据库（如Milvus、Chroma、Qdrant）中检索出与问  
      题向量最相似的Top-K个文本块。这一步本质是“近似最近邻搜索（ANN）”，常用算法有HNSW、IVF等，核心指标是召回率（Recall）。
   6) 重排序（Rerank）  
      向量检索返回的Top-K结果只是“语义相似”，但不一定“最相关”。Rerank层的作用是引入一个更精密的交叉编码器（Cross-Encoder）模型，对检索  
      结果进行精细化重排。与向量检索（双塔模型）相比，Rerank模型计算更慢但精度更高。这一步通常会将候选集从几百个压缩到最终送给LLM的Top-3或  
      Top-5。
   7) 增强生成（Augmented Generation）  
      最后，将重排序后的Top-N个文本块作为“参考资料（Context）”，连同用户的原始问题一起，构造成一个精心设计的Prompt，喂给大语言模型（LLM）。  
      LLM根据参考资料生成最终答案。核心要点是：通过System Prompt约束模型“依据资料回答，不要胡编”，从而有效降低幻觉。
   8) Q1：Chunking时，你一般怎么确定Chunk Size？有没有遇到什么问题？  
      ans：没有固定最优值，取决于文档类型和下游LLM的窗口长度，一般从512~1024tokens试起，用重叠窗口（overlap）保证上下文不丢失。遇到过的问题：  
      切分时把完整的表格或代码块切碎了，导致语义不完整。解决方案是按特定的分隔符（\n\n、表格边界）做递归切分。
   9) Q2：你怎么评估你选的Embedding模型好不好？  
      ans：不能只看MTEB排行榜，要结合业务数据做端到端评测。常用的指标是Recall@K（Top-K中命中的比例），用Ragas等框架做自动化评测。通常会准备  
      一个“问题-标准答案-上下文”三元组的测试集，离线对比不同模型的召回率。
   10) Q3：向量检索和Rerank的区别是什么？为什么不能只用向量检索？  
      ans：向量检索是“粗筛”（双塔模型，计算快，精度相对低），Rerank是“精排”（交叉编码器，计算慢，精度高）。先用向量检索从海量数据中快速缩小范围  
     （百万级到百级），再用Rerank在百级候选中精准排序，这是“系统性能与精度平衡”的经典设计。
   11) Q4：你的RAG系统出现过“检索到错误资料导致回答错误”的情况吗？怎么处理？  
      ans：出现过，这是典型的数据质量问题。处理策略分三层：数据源头治理，清洗低质量文档，标注数据来源的“可信度等级”；检索阈值过滤：设置相似度阈  
      值，低于阈值的直接不召回，告诉用户“资料库中没有相关信息”；生成时加约束：Prompt中强制要求LLM“若参考资料中无答案，直接说不知道，不要推测”。
   12) Q5：什么是HyDE？你知道它的原理吗？  
      ans：HyDE（Hypothetical Document Embeddings，假设性文档嵌入）。核心思想是：先让LLM根据用户问题生成一段“假设性的答案文档”，再拿这个假设答案  
      去向量库检索。这样做的目的是缩小问题与文档之间的语义差距，提升召回率。但缺点是增加了LLM调用延迟。
   13) Q6：你用过哪些向量数据库？为什么选它？  
      ans：用过Chroma（轻量级，适合原型验证）；Milvus（生产级，支持分布式，性能强）。选型考量点：数据量规模、查询QPS要求、是否有过滤条件（标量+向量混合检索）。
   14) Q7：整个链路里，最耗时的环节是哪个？你怎么优化的？  
       ans：主要耗时在LLM生成（几百毫秒到几秒）和向量检索（尤其是大规模数据）。优化策略：生成加速，用vLLM部署，流式输出（SSE）；检索加速，建好索引，用GPU加速ANN计算；缓存，对高频Query做语义缓存（Semantic Cache），命中后直接返回，不再走全链路。
   15) 离线知识库型RAG和实时数据  
       以上是针对离线知识库型RAG的流程。如果业务场景是实时数据（如导航中的实时路况），我还会引入Tool Use（Function Calling），让Agent主动调用外部API获取实时信息，与RAG形成互补。
   
2. 掌握LangChain框架    
   1) 什么是LangChain?  
      一个 Python 框架，封装了调用大模型时重复的样板代码，提供标准化组件让你搭积木一样开发 AI 应用。
   2) LangChain 的核心组件有哪些？   
      Model（模型）、Prompt（提示词）、Chain（固定流程）、Memory（记忆）、Retriever（检索器）。Agent 是高阶能力，让AI自主决策。
   3) Chain 和 Agent 的区别？  
      Chain 是你提前定好路线图，AI 按部就班执行；Agent 是给 AI 一个目标，它自己决定走哪条路、用什么工具。
   4) 你在华为怎么用 LangChain 的？   
      用 LangChain 的 RetrievalQA 链构建了 RAG 系统，把导航故障文档存成向量库，问题定位时检索相关故障记录，交给 LLM 生成诊断建议。

3. 掌握LlamaIndex框架
   1) LlamaIndex是什么？  
      LlamaIndex是一个专为RAG场景设计的数据框架，它的核心价值在于能高效地将大模型与私有数据连接起来。它的工作流程主要分为数据索引和查询检索两个阶段：前者负责从PDF、SQL等160多种数据源加载数据，并将文档切分、向量化后建成索引；后者则负责将用户的问题通过语义检索找到最相关的文本块，最后连同用户问题一起提交给LLM，生成有据可循的答案。
   2) LlamaIndex与LangChain的核心区别？  
      LlamaIndex更聚焦于检索质量这个单一问题，提供更细粒度的控制。而LangChain的优势在于更通用的流程编排，适合构建复杂的Agent。在实践中，我可能会考虑将LlamaIndex的检索器作为一个工具，集成到LangChain的流程中去使用，来发挥它们各自的优势。

4. 具备Function Calling开发经验
   1) Function Calling是什么  
      Function Calling 是我实现 Agent 和连接外部系统的关键手段。它的本质是让LLM通过输出结构化的JSON，来明确表达它需要调用什么外部函数以及传什么参数。在我的项目中，我会先定义好工具的JSON Schema（即函数声明）。当用户提出需求时，LLM会返回一个结构化的调用指令。我的应用层会解析这个指令，安全地执行对应的本地函数（如数据库查询、API调用），最后将执行结果返回给LLM，让它生成最终的回复。这个机制确保了LLM与现有系统之间交互的可靠性和准确性。

6. 具备ReAct Agent设计经验
   1) ReAct Agent是什么？  
      ReAct 是我实现复杂 Agent 任务的核心设计范式。我将它理解为一种‘思考-行动-观察’的循环推理模式，它让 Agent 能够自主地将一个复杂的大目标拆解成一系列可执行的小步骤，并根据每一步的执行结果动态地调整自己的后续行动。
   2) ReAct Agent实践  
      我会这样实现一个 ReAct Agent：首先，我会为模型提供一个结构化的 Prompt，清晰定义它的可用工具集和思考格式。当用户提出一个复杂的任务后，模型会进入 ReAct 循环，每一步都包含明确的 Thought（思考下一步该做什么）、Action（调用具体的工具）、Observation（分析工具返回的结果）。这个过程会一直持续，直到模型认为已获得足够信息，最终给出 Final Answer。

7. 熟悉Prompt Engineering
   1) 核心方法论
      零样本提示（Zero-shot）：直接提问，不给示例。使用模型已充分理解的任务（如翻译、摘要）。  
      少样本提示（Few-shot）：在问题前，先给模型看1-3个“标准示例”（输入->输出）。适用于需要模型模仿特定格式、语气或进行复杂分类的任务。  
      链式思考（Chain-of-Thought,CoT）：引导模型在给出最终答案前，先“展示其推理过程”。适用于数学题、逻辑推理、需要多步骤分析的任务。  
      自洽性（Self-Consistency）：让模型“想”很多次（多次采样），然后投票选出最一致的答案。  
      思维树（Tree of Thoughts,ToT）：让模型像下棋一样，探索多种“思考路径”，并自我评估哪条路更优。 

8. 熟悉System Prompt调优方法论  
   1) System Message（系统消息）  
      给模型设定的“人设”和“底层规则”。它是对话的“宪法”，一旦设定，会在整个对话过程中持续生效。
   2) User Message（用户消息）  
      用户当前提出的具体问题或指令。
   3) 为什么System Prompt如此重要？  
      定义了模型的“角色”；设立了“行为边界”；决定了“输出风格”
   4) 核心调优方法论（如何写好 System Prompt）  
      角色扮演 (Role-Playing)：为模型分配一个明确的、具体的角色。  
      约束与边界 (Constraints & Boundaries)：明确告诉模型“能做什么”和“绝对不能做什么”。  
      目标与格式 (Goal & Format)：清晰地定义模型需要完成的任务和输出的格式。  
      思维链引导 (CoT Guidance)：在 System Prompt 中，直接指示模型“在回答前进行分步思考”。  
      迭代优化 (Iterative Optimization)：将调优视为一个实验过程。不断测试不同的措辞、顺序、约束，观察输出的变化，并持续改进。

二、模型训练、调参与推理优化
1. 了解SFT（监督微调）技术  
   1) 监督微调（SFT，Supervised Fine-Tuning）是什么？  
      是让大模型从一个‘通才’变为‘专才’或‘得力助手’的关键一步。它通过使用高质量的‘指令-回答’数据进行训练，教会模型如何遵循指令、进行对话，而不是简单地续写文本。
   2) SFT 的关键技术细节  
      训练数据的“配方”：质量比数量更重要，  
      数据结构：工业界常用的SFT数据不是简单的“指令-回答”对，而是多轮对话的格式  
      数据生成方法：Self-Instruct：用少量高质量的种子示例，让强大的模型（如GPT-4）自己“出题”生成更多指令数据，再经过人工筛选和过滤；Evol-Instruct：从简单指令出发，通过“加深”、“加宽”、“具体化”等操作，让模型把简单的指令一步步“进化”成更复杂的指令，从而获得难度分层的多样化数据  
   3) 训练方式的区别：全参微调 vs. 高效微调  
      全参微调 (FFT)：模型所有参数都参与训练，全部更新。  
      高效参数微调 (PEFT)：冻结原始模型的大部分参数，只训练一小部分新增的参数，其中最主流的是LoRA。
   4) 常见陷阱与应对策略  
      “灾难性遗忘”（Catastrophic Forgetting）：模型过度学习SFT数据，导致忘记了它在预训练时学到的通用知识，感觉模型“变笨”了。对策：在SFT数据中混入一部分通用数据，使用较小的学习率（Learning Rate）进行训练，训练完成后用一个轻量的SFT任务把通用能力“拉回来”  
      过拟合（Overfitting）：模型把训练数据“背”下来了，而不是学会了泛化能力，导致面对新问题时表现不佳。对策：使用Early Stopping（在验证集效果不再提升时提前停止训练）

2. 了解LoRA/QLoRA（低秩适配）微调技术  
   1) LoRA核心原理  
      低秩假设：在微调过程中，模型权重的变化量 ΔW 可以用一个低秩矩阵来近似表示。原始全参微调需要更新整个权重矩阵 W（假设维度为 d × k）。而 LoRA 将 ΔW 分解为两个小矩阵的乘积：ΔW = B × A，其中：A 的维度为 r × k（随机高斯分布初始化），  
      B 的维度为d × r（零矩阵初始化），r是一个远小于d和k的秩，通常取4、8、16或32，前向传播时，公式变为：h = W₀x + BAx。训练时只更新 A 和 B，W₀被冻结。这个设计让可训练参数量从d×k骤降到r × (d + k)，当r远小于d和k时，参数量可减少10000倍以上
   2) 为什么 LoRA 如此重要？  
      需要训练的参数通常不到模型总量的0.1%，显存要求很低，训练速度约3~5倍速度提升，每个任务只需存储一个LoRA适配器文件（约几十MB）  
   3) QLoRA的极致性价比：  
      4-bit NormalFloat (NF4) 量化：比传统4-bit量化精度更高，更好地适配正态分布的模型权重。  
      双重量化（Double Quantization）：对量化常数也做量化，进一步节省约0.37%的额外显存。  
      分页优化器（Paged Optimizers）：利用NVIDIA统一内存，在显存不足时自动将数据暂存到CPU内存，避免OOM（显存溢出错误）。  
      LoRA 微调：在量化后的4-bit模型上挂载LoRA适配器，训练时只有LoRA参数用FP16精度计算，更新梯度。

3. 熟悉GPTQ/AWQ模型量化方案  
   1) 什么是模型量化？  
      量化就是把模型参数中占据大量空间的高精度数字（如 FP16 或 BF16），用更低精度的数字（如 INT4 或 INT8）来表示，从而达到压缩模型体积、降低显存占用、加快推理速度的目的。  
   2) GPTQ与AWQ的对比  
      GPTQ：逐层补偿，做完量化后看看哪层损失最大再微调回来。适合纯文本大预言模型。极致压缩
      AWQ：保护重点，量化前先分析，找出对模型输出重要的参数，重点保护它们。适用于多模态模型。看中模型性能

4. 了解vLLM推理框架部署流程  
   1) 为什么选择 vLLM 而不是直接用 Transformers 加载模型？  
      vLLM 解决了传统推理框架的两个核心痛点：显存管理低效：传统框架为 KV Cache 预分配连续显存，大量空间被浪费，显存利用率通常只有40%左右。vLLM 的 PagedAttention 技术借鉴操作系统的虚拟内存和分页机制，将 KV Cache 分页管理、按需分配，显存利用率可提升至90%以上，并消除了显存碎片化问题。请求处理僵化：传统框架用固定批大小（batch size），容易造成GPU空闲或溢出。vLLM 的连续批处理（Continuous Batching） 能动态合并、调度请求，使吞吐量达到传统框架的2-4倍。  
   2) 部署流程：  
      首先确认GPU硬件和CUDA环境满足要求。部署上，我更倾向于使用官方 Docker 镜像，这样环境更干净、可移植性也好。启动服务时，关键参数需要根据模型来设定，比如用 --quantization 指定量化格式，用 --gpu-memory-utilization 控制显存水位。为了让服务更稳定，我会把运行命令固化到 Docker Compose 配置里，方便管理和重启。如果未来有更大规模的部署需求，也可以考虑进一步迁移到 Kubernetes 集群。

5. 掌握Ragas等RAG评测框架
   1) Ragas是什么？  
      Ragas是目前RAG系统评估领域的事实标准框架。它的核心价值在于：用LLM来自动评估LLM的RAG系统表现，把RAG调优从“凭感觉”变成“看数据”。
   2) 为什么需要 Ragas？  
      RAG有一个致命的“隐形失败模式”：模型可能把假信息编得跟真的一样，用户根本分辨不出来。比如用户问的是公司政策，模型却“胡编”了一个政策原文——用户以为查到了官方信息，实际上被误导了。Ragas 的回答是：通过四个核心指标，把 RAG 系统的“检索”和“生成”两个环节拆开打分，精准定位哪个环节出了问题。  
   3) Ragas 从两个维度、四个指标来量化 RAG 系统的表现  
      检索维度：上下文精确度（Context Precision），检索回来的文档里，真正相关的占比多少？相关的是否排在前面？  
      检索维度：上下文召回率（Context Recall），该召回的相关文档，有多少被真正召回了？  
      生成维度：忠实度（Faithfulness），模型生成的答案，是否完全基于检索到的上下文？有没有在上下文之外编造？  
      生成维度：答案相关性（Answer Relevancy），模型的回答是否直接针对用户问题？有没有说废话或跑题？
   4) 忠实度（Faithfulness）——防幻觉的关键指标  
      Faithfulness的计算原理（两阶段LLM调用）。  
      第一阶段（声明提取）：先让一个 LLM 把模型生成的“答案”，拆解成若干条“原子级的事实声明”（Atomic Facts）。例如，“RAG 是 2020 年由 Facebook AI 提出的技术”会被拆成三个独立的声明：“RAG 是 2020 年提出的”、“RAG 由 Facebook AI 提出”、“RAG 是一种检索增强生成技术”。  
      第二阶段（支撑验证）：针对每条声明，让 LLM 判断“这个声明能否从检索到的上下文中被推断出来”。能推断出来的就算“忠实”，推断不出来就算“不忠实”。  
      最终计算：Faithfulness = 被支撑的声明数 / 总声明数
   5) 上下文精确度（Context Precision）——测“检索噪音”  
      衡量检索到的文档中，有多少是真正相关的。它采用“位置加权”的方式，排在前面的文档权重更高。  
      计算方式（简要）：对检索返回的每个文档，让 LLM 判断是否与问题相关（1相关/0不相关），然后按“前面相关、后面不相关”的理想排序进行加权计算。低分意味着检索噪音太大，模型拿到一堆不相关的资料。
   6) 上下文召回率（Context Recall）——测“检索遗漏”  
      衡量“标准答案”里的知识点，检索到的文档里覆盖了多少。计算方式：从标准答案（Ground Truth）中提取出原子声明，然后判断每个声明能否从检索到的上下文中推断出来。能推断出来的占比就是 Context Recall。低分意味着切片策略太粗、Chunk Size 过大或检索 Top-K 太小，把关键信息漏掉了。
   7) 答案相关性（Answer Relevancy）——测“回答是否切题”  
      衡量模型生成的回答是否直接针对用户问题。计算方式：让 LLM 根据模型生成的“答案”，反向推理出可能的问题，然后计算“用户真实问题”和“反向推理出的问题”之间的 Embedding 相似度，取平均值。
